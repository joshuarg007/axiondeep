Engineering Blueprint

Caracol Peninsula Gate Access System

1. Overview

A complete license-plate-recognition (LPR) gate access system for one HOA gate (one entry + one exit lane). Sold as a productized platform: HOA pays $2,999 setup + $1/home/month for access. We retain ownership of the platform IP. Caracol Peninsula is the first deployment; the architecture must replicate to other communities with minimal per-deployment engineering.

Components

  • 2x AI cameras (entry + exit) with ALPR + MMR (make/model recognition)
  • 1x on-site edge processing unit (mini PC)
  • 1x gate relay interface to the existing gate operator
  • AWS cloud backend (multi-tenant)
  • React Native mobile app (iOS + Android) for every homeowner
  • React web admin console for the HOA board
  • Optional: cellular gateway if the site lacks internet

Out of scope for v1

  • RFID / fob credentials (require additional gate hardware; secure visitor codes handle the same use case)
  • Facial recognition
  • Integrated Airbnb/VRBO API auto-provisioning (data model leaves a hook; not built in v1)
  • Multi-gate sites (architecture supports it; not in Caracol's deployment)

4. Network & Security Design

On-site network

  • Edge unit + cameras isolated on a dedicated LAN segment
  • Static local IPs: 192.168.50.10 (edge), 192.168.50.11 (cam entry), .12 (cam exit), .13 (relay)
  • Cameras have no internet route. RTSP/ONVIF stays local
  • Edge unit is the only device with outbound internet, restricted by UFW to:
  • TLS 443 to our API Gateway endpoint
  • NTP (chrony)
  • APT updates (Ubuntu mirrors)
  • No inbound services. Remote management via Tailscale (only the edge unit is on the tailnet).

Cloud transport

  • TLS 1.2+ everywhere
  • Edge unit auths to API Gateway with an AWS IAM-Signed-V4 request using a per-unit IAM role (via Cognito Identity Pool for unauth → temporary credentials), OR a long-lived signed JWT bound to a community + edge-unit-id claim. (Pick one in implementation; IAM SigV4 is more AWS-native.)
  • Backend rejects any event from an unknown edge identity

Camera hardening

  • Default admin password rotated at install; credential stored in our 1Password vault
  • Firmware locked to a known-good version; auto-update disabled
  • ONVIF disabled unless required; RTSP credentials random per camera

Edge unit hardening

  • Ubuntu Server 24.04 LTS
  • CIS Level 1 baseline (cis-audit-tool or equivalent script)
  • SSH: pubkey-only, no passwords, Tailscale-only
  • unattended-upgrades for security patches
  • auditd with sensible default rules
  • All app processes run as a non-root gateops user

Gate relay

  • Shelly Plus 1 on local LAN, no internet
  • HTTP auth: long random API key in edge unit's env
  • Relay endpoint only callable from 192.168.50.10

Data privacy

  • Plate images encrypted at rest (S3 SSE-S3 at minimum, SSE-KMS for production)
  • Default retention: 30 days; configurable per community
  • LPR only; no facial recognition, no occupant data
  • Mexico (LFPDPPP) and US (state-specific) data-processor terms in the HOA agreement
  • Right-to-delete honored per resident on board request

Multi-tenancy

  • One table for all communities (no per-tenant infrastructure)
  • All partition keys prefixed with COMMUNITY#<slug>
  • Edge unit identity bound to its community via Cognito custom attribute
  • Cognito user pool groups: community-<slug>
  • Each user's JWT carries their community claim; Lambda enforces tenant isolation on every read/write

6. ALPR / AI Pipeline

Plate recognition

Primary: CodeProject.AI Server with the License Plate Reader module on the edge unit. - Free, OSS, runs locally - ~90-95% accuracy on US/Mexico plates - ~150-400 ms per inference on the N100 with Coral TPU optional

Fallback: Plate Recognizer Cloud API - Only invoked when local confidence < 0.85 - ~$50-100/mo per 50k reads - Higher accuracy, supports Mexican plate formats

Make / Model / Color Recognition (MMR)

  • Plate Recognizer also returns MMR on every cloud-fallback read
  • For local-only reads, MMR via MMR-Net or similar OSS model (slower but free)

Service vehicle classification

Combined approach:

  1. Plate registry. Per-community list of known service plates: local police, trash company, USPS/UPS/FedEx/Amazon DSP/DHL, water utility, propane delivery. Admin maintains. Auto-tag in feed and admin console.
  2. MMR + visual heuristics. Body type + color + commercial markings → likely-class inference. Lower confidence; presented as [Likely USPS] rather than asserted.
  3. Resident reporting. Residents who recognize a service vehicle can tag it; with 2+ confirmations and admin review, the plate enters the community's known list.

9. Identity & Auth

Cognito design

  • One user pool across all communities (cheaper, simpler federation)
  • Custom attribute community (string slug)
  • Groups: homeowner, airbnb-host, board-admin, super-admin
  • MFA required for board-admin and super-admin
  • Password policy: 12+ chars, mixed case + number + symbol

Sign-up flow

  • Board uploads resident roster (CSV) in the admin console
  • System sends invite emails with one-time tokens
  • Resident sets password on first visit; account auto-attached to their community + unit
  • Email verification required before first vehicle registration

Tokens

  • Access token: 1 hour
  • Refresh token: 30 days, rotated on use
  • Lambda authorizer validates community claim on every request

Edge unit identity

  • Per-edge-unit IAM role via Cognito Identity Pool (unauth → temp creds)
  • Edge unit holds an installation secret stored in /etc/gateops/secret
  • All edge-unit API calls signed with AWS SigV4

10. Visitor Code Lifecycle

Code format

  • 6-character base32 (no I, O, 0, 1) - ~1 billion combinations
  • Stored as HMAC-SHA256 hash, never plaintext in DDB
  • Single-use OR multi-use bounded by window

Generation

POST /visitor-codes
{ window: "single" | "today" | "range",
  validFrom?, validUntil?, expectedPlate?, label? }

Lambda generates code, stores hash + metadata in DDB with TTL = validUntil + 24h, returns plaintext code to caller (one-time response).

Delivery

  • App returns the code; user shares via the OS share sheet (SMS, WhatsApp, email)
  • Optional v1.1: app sends SMS via AWS End User Messaging (~$0.0075/msg)

Validation at the gate

  • Guest enters code on the intercom keypad
  • Edge unit calls POST /visitor-codes/validate with the code
  • Lambda hashes + looks up + checks window + marks used (if single-use)
  • Response: { allow: true | false, reason? }
  • Edge unit triggers relay if allowed

Bypass via plate

  • Guest can also send their plate to the host ahead of time
  • Host enters it in the visitor code record
  • Camera auto-recognizes that plate during the window → opens gate without code entry

11. Airbnb Host Mode

Host enrollment

  • Homeowner emails the board requesting host status, OR board enables it for known short-term-rental owners
  • Admin console toggles the airbnb-host group for the user

Stay model

{ stayId, hostId, guestName, checkIn, checkOut,
  codes: [ visitorCodeId ], plates: [ expectedPlate ] }
  • Host creates a Stay
  • System auto-generates a visitor code valid for the stay window
  • Host can add multiple codes (for guest's family) all bound to the stay
  • All codes invalidate automatically at checkOut

Future hook: PMS integration

  • Webhook endpoints designed in for Airbnb / VRBO / Hostfully
  • Not wired in v1; data model anticipates it

12. Payment-Status Gating

Admin control

  • Each resident has a paymentStatus: active | suspended | grace
  • Default active
  • Admin sets via console; change logged with timestamp + admin id + optional reason

Enforcement

  • suspended: app shows banner; vehicle plates no longer auto-trigger relay; visitor codes denied
  • grace: same access as active but app shows a payment-due banner
  • active: full access

Physical override

  • Suspended resident at the gate: call box still rings the board / security
  • HOA decides escalation path (we do not lock people out of their homes by default)

Reactivation

  • Admin toggles back to active → all access restored within ~5 seconds (DDB → edge cache invalidation push)

13. Install Procedure

Pre-deployment (off-site, ~1-2 weeks for first community)

  1. Order hardware (lead time 5-10 days)
  2. Image edge unit: Ubuntu 24.04, CodeProject.AI, our gateops service, Tailscale
  3. End-to-end smoke test on the bench (known test plates)
  4. Configure per-community settings: slug, branding, Cognito group, initial roster
  5. Pack and ship

For the first deployment (Caracol), this pre-deployment overlaps ~4 weeks of platform finalization work that does not repeat for later communities.

On-site install (1 day, 6-10 hours)

  1. Site survey: confirm camera mounting points, power, network access, gate operator dry-contact input
  2. Mount cameras: entry + exit, ~4-8 ft height, angled for 15 ft capture distance
  3. Run PoE cables from each camera to the switch
  4. Connect switch → edge unit → cellular gateway (or wired internet)
  5. Wire gate relay to the existing gate operator's open input
  6. Calibrate: drive a known plate through several times; verify capture, classification, relay trigger
  7. Board walkthrough of the admin console
  8. Send resident invitation emails

Post-install (2 weeks)

  • Daily uptime + accuracy check
  • Tune ALPR confidence threshold
  • Build initial known-service-vehicle list from observed traffic
  • One-week and two-week board check-ins

14. Security Review Checklist

Infrastructure

  • [ ] Edge unit OS hardened to CIS Level 1
  • [ ] All default device passwords rotated and stored in 1Password
  • [ ] No inbound ports on the edge unit
  • [ ] Tailscale ACL restricts who can SSH the edge unit
  • [ ] Cellular gateway firewalled; no port-forwarding
  • [ ] AWS root account MFA + no programmatic keys
  • [ ] IAM roles per service; no *:* policies
  • [ ] All cloud traffic TLS 1.2+
  • [ ] DynamoDB encryption at rest (default)
  • [ ] S3 plate-image bucket private; served only via CloudFront signed URLs
  • [ ] CloudFront origin access control restricts direct S3 access
  • [ ] Secrets in AWS Secrets Manager; nothing in env vars
  • [ ] CloudTrail logging enabled on all regions

Identity

  • [ ] Cognito MFA enforced on admin roles
  • [ ] Password policy: 12+ chars + symbol + number + mixed case
  • [ ] Refresh-token rotation on use
  • [ ] Lambda authorizer validates community claim on every request
  • [ ] No PII in CloudWatch logs (scrubbed in Lambda)

Application

  • [ ] Visitor codes generated with cryptographic RNG; stored as HMAC-SHA256
  • [ ] Single-use codes flagged on first redemption (atomic conditional update)
  • [ ] Rate limits on /visitor-codes/validate (5/sec/edge-unit)
  • [ ] Input validation on every API endpoint (Zod schemas)
  • [ ] CORS limited to known origins (admin console domain, mobile app bundle ID)
  • [ ] CSP on admin console: default-src 'self'

Data

  • [ ] 30-day retention default on plate images
  • [ ] Right-to-delete honored per resident
  • [ ] Data Processing Agreement signed with HOA (LFPDPPP / GDPR)
  • [ ] Audit log immutable for 90 days (DynamoDB streams → S3 Object Lock)
  • [ ] Annual penetration test once we exceed 5 deployments
